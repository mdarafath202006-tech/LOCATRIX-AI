01 / PROJECT OVERVIEW

Designed for signal-challenged spaces.

Satellite navigation can degrade indoors, underground, around tall buildings, and near obstructed structures. LOCATRIX investigates how on-device sensors could help estimate local movement between reliable external position fixes.

⌁

The problem

GNSS signals can be blocked, reflected, or too weak to provide stable positioning. A continuous satellite fix cannot be assumed in every environment.

IndoorUndergroundUrban canyon
⌖

The approach

Estimate relative movement from inertial measurements and, where available, camera-derived visual motion. Combine evidence to reduce the weaknesses of any single sensor.

IMUVisual cuesSensor fusion
⇢

The intended outcome

A local trajectory estimate with uncertainty and measurable drift, sent through a Bluetooth-linked LoRa node to a gateway and web dashboard when the gateway has internet access.

Relative trackOffline-capable goal

03 / END-TO-END WORKFLOW

From raw signals to a local path.

This is the planned engineering pipeline. Each stage has a specific input, processing responsibility, and output that can be tested independently.

Collect sensor streams

Read timestamped accelerometer and gyroscope data. Optionally capture camera frames and device metadata with user permission.

Input · raw signals

Synchronize & preprocess

Align timestamps, handle missing samples, filter noise, estimate orientation, and normalize units into a consistent frame.

Output · aligned samples

Estimate pedestrian motion

Detect candidate steps and heading changes, or estimate camera-relative motion when visual features are reliable.

Output · motion increments

Fuse sensor evidence

Combine motion estimates and their confidence using a defined filter or estimator; reject inconsistent measurements where possible.

Output · relative pose

Build trajectory

Integrate accepted motion increments into a local coordinate frame while tracking uncertainty and accumulated drift.

Output · X/Y path

Optional AI assistance

After data collection, train and validate a bounded model for a chosen task such as step-event classification or motion-quality estimation.

Output · model prediction

Evaluate against reference

Compare estimated trajectories with a measured reference path; calculate error by segment, final displacement, and drift over time.

Output · metrics report

Present & share results

Display the local path, source availability, quality indicators, and limitations. Offline sharing requires a separate transport design.

Output · user interface

05 / OFFLINE COMMUNICATION DESIGN

Phone → Bluetooth → LoRa → Gateway → Dashboard.

LOCATRIX is designed so a user's phone does not need mobile data or Wi-Fi to send a location update. Position estimation and long-range communication are separate subsystems: the phone estimates local movement; the radio link transports the update.

Estimate movement on phone

Accelerometer, gyroscope and heading sensors feed pedestrian dead reckoning and the planned AI-assisted estimation pipeline. A starting reference is needed and drift must be measured.

Phone · local computation

Bluetooth to LOCATRIX node

The phone sends a compact location/trajectory update over Bluetooth to a separate paired LOCATRIX hardware node. Bluetooth is the short-range phone-to-device link.

BLE / Bluetooth

Transmit over LoRa

The hardware node sends a small packet over LoRa to a reachable LoRa receiver or gateway. LoRa is the radio communication layer; it does not calculate the user's position.

LoRa · long-range, low data rate

Gateway and dashboard

A gateway forwards received packets to the backend/cloud when it has internet access. The web dashboard can then show the latest reported user position to authorized viewers/admins.

Gateway → cloud → web

Important: the phone and LoRa node can communicate without internet, and LoRa radio can carry packets without internet. A live cloud dashboard needs a gateway with internet backhaul; if all internet is unavailable, cloud updates wait until a connected gateway can forward them. LoRa coverage, local regulations, radio hardware and packet delivery must be tested.
Hardware reality: ordinary smartphones do not normally transmit LoRa directly. A separate LoRa-capable device is needed for each mobile endpoint that must send/receive LoRa, paired to its phone over Bluetooth. A receiving user can use their own paired node/phone, or a gateway can receive reports centrally. Exact hardware and topology are implementation decisions, not features proved by this UI demo.

06 / AI & SENSOR FUSION

Use AI where it can be measured.

LOCATRIX should not treat “AI” as a magic accuracy switch. The model, labels, baseline, and evaluation procedure must be specified before claiming an improvement.

01

Define one ML task

Candidate task: classify motion windows as walking, stationary, or uncertain using engineered features from accelerometer and gyroscope sequences. This is a proposal, not a trained model claim.

02

Build a reproducible dataset

Record timestamped sensor windows across participants and walking conditions, with consent and reference labels. Split training and test data by trial or participant to reduce leakage.

03

Compare against a baseline

Start with threshold-based step detection or a simple statistical model. Report F1-score for event classification and positioning error for the trajectory; do not confuse the metrics.

09 / PANEL-READY EXPLANATIONS

Questions you may be asked.

Use precise wording during your review: distinguish what the prototype shows from what the complete system is intended to achieve.

Does LOCATRIX completely replace GPS?

The goal is to estimate relative movement when GNSS is unreliable. Without an external reference or known starting point, the system cannot promise globally accurate latitude and longitude, and inertial drift accumulates.

Where exactly is the AI?

The current demo does not contain an integrated, trained AI model. A future ML task must be defined, trained on documented data, and evaluated against a baseline before we can claim a benefit.

Can it work without internet?

On-device sensing and local estimation can be designed to work offline. Sharing a location to another phone without internet needs a separate communication link such as Bluetooth, Wi-Fi Direct, or suitable radio hardware, with range and reliability constraints.

How will accuracy be proved?

Run repeatable routes and compare the estimated local trajectory with a measured reference. Report RMSE or MAE, final position error, and drift over time or distance; include the test setup and limitations.

Why use sensor fusion?

Different sensors fail in different ways. Combining motion and visual evidence can improve robustness if their uncertainties are modelled properly; fusion does not guarantee accuracy on its own.

What does this demo currently prove?

It demonstrates the user-interface concept and intended workflow using simulated movement. It does not prove live positioning, camera tracking, trained AI, radio messaging, or measured accuracy.
